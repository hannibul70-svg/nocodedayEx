# 코드 작성 원칙 (Antigravity Code Principles)

코드를 작성하거나 수정할 때 아래 15개 원칙을 지킨다. 원칙끼리 충돌하면
우선순위는 **가독성 > 단순성 > 중복 제거 > 짧음**이다.

## 기본 5원칙
1. **가독성을 최우선으로 한다.** 읽는 사람 기준으로 코드를 짠다 — 코드는
   쓰는 시간보다 읽히는 시간이 훨씬 길다.
2. **코드는 짧을수록 좋다 — 단, 목표가 아니라 결과다.** 가독성을 해치면서까지
   줄이지 않는다.
3. **진입점(main)은 짧게 유지한다.** 흐름만 보여주고 세부 로직은 이름 붙은
   함수로 위임한다.
4. **변수/함수 이름은 실제 의미에 맞게 짓는다.** 이름만 보고 용도를 알 수
   있어야 한다.
5. **불필요한 반복(중복 코드)을 만들지 않는다(DRY).** 같은 로직을 여러 곳에
   복붙하면 하나만 고치고 나머지를 잊기 쉽다.

## 구조/설계
6. **단일 책임 원칙(SRP)을 지킨다.** 함수·모듈 하나는 한 가지 이유로만
   바뀌어야 한다.
7. **결합도는 낮게, 응집도는 높게 유지한다.** 모듈끼리는 최소한만 알고,
   모듈 안 요소들은 서로 밀접하게 관련되어야 한다.
8. **한 함수 안에서 추상화 수준을 섞지 않는다.** 고수준 로직과 저수준
   디테일을 같은 함수에 두지 않는다.
9. **YAGNI.** 지금 필요 없는 유연성/확장성을 미리 설계하지 않는다.

## 가독성/명명
10. **이름으로 거짓말하지 않는다.** 함수 이름과 실제 동작이 어긋나면 안 된다
    (예: `getUser()`가 DB에 쓰기까지 하면 안 됨).
11. **매직 넘버/문자열을 쓰지 않는다.** 의미 있는 상수·enum으로 뺀다.
12. **guard clause(조기 반환)로 중첩을 줄인다.** 예외/실패 조건을 먼저
    걷어낸다.

## 안정성/유지보수
13. **실패를 조용히 삼키지 않는다.** 에러는 명시적으로 처리하거나 전파한다.
14. **순수 함수와 부작용(DB/네트워크)을 분리해 테스트 가능한 구조로 만든다.**
15. **스타일 일관성을 지키고, 변경은 검토 가능한 작은 단위로 나눈다.**

## 자가 점검 (코드 작성 직후)
- 방금 쓴 코드가 다른 파일의 로직과 대부분 같은가? → 원칙 5 위반 가능성,
  공통 함수 추출을 검토한다.
- 상수 없이 숫자/문자열 리터럴을 조건문에 그대로 썼는가? → 원칙 11 위반,
  이름을 붙인다.
- 하나의 함수가 서로 다른 이유로 바뀌어야 하는가? → 원칙 6 위반 가능성,
  분리를 검토한다.
- 의도적으로 원칙을 벗어나야 하는 경우, 주석에 "왜"를 남긴다.
